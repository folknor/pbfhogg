The main defects are in inspect's reporting and statistics. These are source-level findings; I changed no files and ran no builds or tests.

1. **[P1] A large `--blocks` limit panics on an otherwise valid file.**  
   [report.rs:293](/home/folk/Programs/pbfhogg/crates/lib/src/commands/inspect/report.rs:293) calculates `limit * 2` without checking overflow. On a 64-bit release build, `--blocks 9223372036854775808` makes that product zero. With any data block present, truncation is selected and the subsequent enormous slice panics. With overflow checks enabled, the multiplication itself panics. This breaks both the flag's limiting behavior and the refusal contract for input-reachable faults. The JSON renderer already uses an overflow-safe comparison.

2. **[P2] `inspect --nodes` measures worker assignment instead of consecutive file coordinates.**  
   [node_stats.rs:180](/home/folk/Programs/pbfhogg/crates/lib/src/commands/inspect/node_stats.rs:180) carries partially filled FOR windows between blobs assigned to each worker, then [finalizes every worker separately](/home/folk/Programs/pbfhogg/crates/lib/src/commands/inspect/node_stats.rs:454). Consider two blobs containing 64 nodes each: the first has latitude zero throughout, the second latitude 900,000,000 throughout. In file order, these form one 128-value window requiring 30 bits. Assigned to separate workers, they become two constant windows requiring zero bits. The histogram, block count and compression estimate change substantially with scheduling or `-j`. The comment claiming that the histogram shape is preserved is false. The right structural change is to order coordinate batches before forming the windows.

3. **[P2] `inspect --show` silently discards metadata it promises to display.**  
   [show_element.rs:196](/home/folk/Programs/pbfhogg/crates/lib/src/commands/inspect/show_element.rs:196) drops present timestamps, changesets and UIDs when their values are zero; `write_user` drops a present empty user. The dense formatter also discards zero values after `DenseNodeInfo::claims()` has established their presence. Neither formatter prints visibility, including `visible=false`. This contradicts [CORRECTNESS.md:187](/home/folk/Programs/pbfhogg/CORRECTNESS.md:187), which explicitly preserves presence and zeros in printing outputs. Consequently absent metadata and explicit zero metadata produce identical displays, and deleted objects lose their visibility state. The formatter is wrong at the boundary from decoded claims to text.

4. **[P2] Default JSON invents a tagged-node count of zero.**  
   The index-only scan [accumulates element counts](/home/folk/Programs/pbfhogg/crates/lib/src/commands/inspect/scan.rs:282) but never counts tagged nodes. Nevertheless, [json.rs:80](/home/folk/Programs/pbfhogg/crates/lib/src/commands/inspect/json.rs:80) unconditionally publishes `"tagged_nodes": 0`. An honest indexed file containing tagged nodes therefore reports zero by default and a positive count under `--distrust-metadata`. This breaks the meaning of that count field without requiring corrupt metadata. The report needs to represent an unmeasured count as unavailable, separately from measured zero.

5. **[P2] `data.objects_ordered` can reject correctly ordered elements.**  
   [scan.rs:426](/home/folk/Programs/pbfhogg/crates/lib/src/commands/inspect/scan.rs:426) derives element ordering partly from the block-layout summary. That summary declares every mixed-kind blob nonstandard. A legal block containing a node group followed by a way group consequently reports unordered objects, although the elements follow canonical order and `check --ids` passes them. Separately, [TypeIdRange](/home/folk/Programs/pbfhogg/crates/lib/src/commands/inspect/types.rs:230) uses signed numeric comparisons: canonical IDs `0, -1, -2, 1` are reported non-monotonic. This breaks [the field's stated meaning](/home/folk/Programs/pbfhogg/crates/lib/src/commands/inspect/keys.rs:47). Element ordering needs decoded group-order evidence and the canonical comparator; block-layout classification answers a different question.

6. **[P2] Timestamp rendering changes the timestamp being reported.**  
   [format_timestamp](/home/folk/Programs/pbfhogg/crates/lib/src/commands/inspect/format.rs:48) accepts milliseconds but discards the fractional part using division toward zero. With `date_granularity=1`, a timestamp of 1500 milliseconds is displayed as `1970-01-01T00:00:01Z`; a timestamp of -1 millisecond becomes the epoch itself. This affects the text report, JSON and timestamp `--get` values. The census explicitly [operates in milliseconds](/home/folk/Programs/pbfhogg/CORRECTNESS.md:238), so its range should retain that resolution when formatted.

7. **[P3] Empty-state sentinels hide accepted values.**  
   [ExtendedStats::has_timestamps](/home/folk/Programs/pbfhogg/crates/lib/src/commands/inspect/types.rs:408) treats `min_timestamp == i64::MAX` as absence. A sole timestamp of `i64::MAX`, with date granularity one, therefore counts as available metadata but produces no timestamp range. [DataBbox::has_data](/home/folk/Programs/pbfhogg/crates/lib/src/commands/inspect/types.rs:357) has the same collision when every decoded latitude equals `i64::MAX`: nodes are counted but their bbox disappears. These values reach inspect through the reader's accepted arithmetic. Explicit optional extrema would preserve the distinction between no observation and an extreme observation.

8. **[P3] Header-only files receive inconsistent reports.**  
   The index-only path returns [indexed=true](/home/folk/Programs/pbfhogg/crates/lib/src/commands/inspect/scan.rs:264), while the decoded path requires [at least one data blob](/home/folk/Programs/pbfhogg/crates/lib/src/commands/inspect/scan.rs:424). Thus adding `--extended`, `--locations` or `--distrust-metadata` changes the same header-only file to indexed=false, contrary to the [documented indexed convention](/home/folk/Programs/pbfhogg/docs/cli/commands.md:729). Also, the extended text renderer [omits metadata coverage entirely](/home/folk/Programs/pbfhogg/crates/lib/src/commands/inspect/report.rs:425) when there are no objects, although the documentation promises `All objects have: (none)`.
