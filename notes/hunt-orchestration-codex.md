# Orchestration performance review

The biggest opportunity is to **decode each artifact once and feed every check that needs it from that reading**. A warm reference cache still leaves the suite repeatedly decompressing PBFs, writing OPL, rereading it, and deleting it. I would rewrite that path and make the suite share producers before adding broad concurrency. The call counts below come from code inspection and depend on which arms run. Wall-time savings are unmeasured.

## 1. Rewrite the suite around shared decoded artifacts

Today a comparison owns its decodes. `opl_compare::walk` runs two `osmium cat` processes serially, waits for both complete OPL files, and then merges them. `order` launches another conversion for keys and counts, although the strict comparison already reads those keys. Both conversions deliberately bypass the persistent cache. The result is repeated work even inside one check. [OPL decode, comparison, and order](/home/folk/Programs/pbfhogg/crates/verify/src/opl_compare.rs:138)

Give each immutable PBF one decoded record source. Feed strict order, duplicate detection, counts, and comparisons from the same ordered scan. Stream single-use outputs directly into their judges. Retain a replayable, block-oriented representation for high-fan-out artifacts such as the base, the updated PBF, the roundtrips, and the locations reference. Keep a bounded memory budget and spill reusable blocks where needed. The check interface needs to accept record sources and scan results in place of paths to temporary OPL. For example, `apply-changes` can merge the osmium stream with its touched-ID model as it reads, collecting osmium's touched records and comparing the expected stream to pbfhogg's output without writing `expected.opl`. The difference listings and their previews still come from the actual compared records. [Apply comparison and expected stream](/home/folk/Programs/pbfhogg/crates/verify/src/checks/apply_changes.rs:341)

Use a **libosmium-backed decoder for osmium-observed claims**. It can initially emit the existing OPL projection through bounded streams, then emit structured records once equivalence is established. Preserve the observable treatment of metadata defaults, visibility, coordinate precision, inline locations, ordered tags and members, and string truncation and escaping. Preserve the distinction between file-sequence comparisons and strict key merges, including the order-specific diagnostics. `ElementReader::into_blocks_pipelined` and `for_each_block_pipelined` already provide ordered, parallel PBF decoding for pbfhogg-native observations. The crate-private fused transforms show how to combine framing, projection, and payload work on decode workers. Keep the independent frame checks and osmium comparisons independent of that reader. [OPL field semantics](/home/folk/Programs/pbfhogg/crates/verify/src/opl_compare.rs:1) [Library reader APIs](/home/folk/Programs/pbfhogg/crates/lib/src/read/reader.rs:330) [Independent frame checks](/home/folk/Programs/pbfhogg/crates/verify/src/pbf_frames.rs:546)

The next payoff from the same design is **fewer reference-generation scans**. One independent base scan can supply per-kind views for `cat`, order and count observations, and stable kind partitions for reencode checks. Today `cat` produces three reference PBFs and decodes them again. The reencode partition path runs three kind-filtered `cat`s and a fourth `cat` to join them. Keep real osmium output wherever a check observes its header, its PBF roundtrip behavior, or its blob packing. For `sort`, consider bypassing the reference sort on inputs independently proved already in the required order, once the exact observed effect of the osmium PBF roundtrip is accounted for. The current multipass sort opens the input once per kind. The simple sort used for refusal counterparts also writes a header claim those counterparts need, so the two artifacts have distinct roles. ## 2. Share fixture producers across checks

Make the change family consume one suite-owned old/new pair and one stripped pair. Both diff checks independently run the same buffered `apply-changes` setup and strip both sides. Repack independently strips the same original input. On the successful sorted, indexed path with an OSC, **four strip launches across the two diffs plus one in repack become two**. The two diff setup applies become one, and the plain `apply-changes` check can consume that same invocation and judge its exit, stderr, header, order, and content when its arguments and model branch agree. That saves five full-file producer launches in the default buffered case. With `--direct-io`, keep the separate direct apply invocation and the buffered diff fixture. The keep-untagged base, refusal cases, indexed and unindexed diff invocations, and all three OSC roundtrip producers retain their distinct roles. [Apply invocation and model branch](/home/folk/Programs/pbfhogg/crates/verify/src/checks/apply_changes.rs:89) [Text diff setup and stripping](/home/folk/Programs/pbfhogg/crates/verify/src/checks/diff.rs:94) [OSC diff stripping](/home/folk/Programs/pbfhogg/crates/verify/src/checks/derive_changes.rs:306) [Repack's stripped-input assertions](/home/folk/Programs/pbfhogg/crates/verify/src/checks/repack.rs:73)

Extend the same ownership to the OSC reading, the osmium-sorted counterpart on claimless input, and the original input's reencode preflight. Plain and locations apply parse the same OSC into separate models, while OSC tags-filter builds another XML/OPL pairing. Share the decoded change occurrences, then bind each model to its own base and policy. Repack and degrade both run the same input framing, index-truth validation, and buffered `check --index`; share their observations and report failures under both checks. For extraction, reuse an identical buffered single-region polygon extract across `extract` and `multi-extract` where present. The latter still needs its sequential single-region baseline and both configured multi invocations where applicable. Its buffered baseline is intentional under `--direct-io`. [Apply model inputs](/home/folk/Programs/pbfhogg/crates/verify/src/checks/apply_changes.rs:233) [OSC listing producer](/home/folk/Programs/pbfhogg/crates/verify/src/verify_change_listing.rs:297) [Reencode preflight](/home/folk/Programs/pbfhogg/crates/verify/src/verify_reencode.rs:90) [Multi-extract baseline and configs](/home/folk/Programs/pbfhogg/crates/verify/src/checks/multi_extract.rs:121)

This is a high-confidence reduction in work. The check-side change is to take a settled artifact **and its producer result**. Each dependent still applies its own assertions and reports its own failure if a shared prerequisite fails. Share only matching inputs and invocation semantics, and keep every pbfhogg producer result run-local.

## 3. Redesign the reference cache around the artifacts checks consume

A hit currently starts `osmium --version` and `ldd`, hashes the executable and its resolved libraries, hashes every declared input, and reads and hashes every stored artifact. A completed miss repeats identity and input hashing before publication, then syncs and hashes the outputs before consumers get them. Dataset resolution already computes an observed digest, which the verifier mostly drops when it extracts the path. A cache hit is recorded as zero time in the check's step breakdown, so this work is absent from the step timings. [Cache execution](/home/folk/Programs/pbfhogg/crates/verify/src/reference_cache.rs:407) [Artifact validation](/home/folk/Programs/pbfhogg/crates/verify/src/reference_cache.rs:172) [Key and tool identity](/home/folk/Programs/pbfhogg/crates/verify/src/reference_cache.rs:573) [Dataset digest](/home/folk/Programs/pbfhogg/crates/devkit/src/datasets.rs:97) [Cache timing](/home/folk/Programs/pbfhogg/crates/verify/src/harness.rs:329)

Resolve tool and input identities once per run, bound to validated file generations. Reuse the observed dataset digest only when the file identity is tied to the hash read. Hold one immutable handle and one validation result per reference artifact per run. Today the cache hard-links artifacts into each check directory, then `Run::watch` makes a full private copy if one of those links becomes an input, because link changes move `ctime`. Owner-held immutable artifacts can serve multiple readers directly. Where a child needs a pathname, give it one stable artifact path for the lifetime of the run. Keep corruption detection and validate content during the consumer's read where possible, with the verdict held until validation completes. [Cache placement](/home/folk/Programs/pbfhogg/crates/verify/src/reference_cache.rs:334) [Watch-time copy](/home/folk/Programs/pbfhogg/crates/verify/src/run.rs:44)

Persist the result that saves the next run the most work. For a CLI-only oracle whose product is consumed solely as records, cache a compact decoded representation instead of retaining a PBF that must be decoded on every hit. Keep actual PBFs where a later CLI needs them. Key reusable products on exact input identity, tool and library identity, operation semantics, and representation version. Keep accepted exit and stderr checks, atomic publication, `--fresh-reference`, the budget, and cleaning behavior. Avoid filling the cache with routine decodes of fresh pbfhogg outputs. The current budget retains recent command artifacts by logical size, so repeated runs can evict useful early entries if the working set exceeds it. The larger payoff is reducing the working set and the work per hit. [Cache retention](/home/folk/Programs/pbfhogg/crates/verify/src/reference_cache.rs:74) [CLI cache flags](/home/folk/Programs/pbfhogg/crates/verify/src/main.rs:65)

## 4. Schedule the remaining work by dependency and resource use

`all` calls each check synchronously with one mutable `Harness`. Inside a check, a launch settles before the next starts, and settlement kills and reaps **every child of the verifier**. Running existing checks on threads would let one launch kill or reap another's children. Split the harness into per-check verdict and diagnostic state, shared immutable artifact ownership, and a process supervisor that can settle each launch tree independently. A dedicated subreaper worker per active launch is one way to preserve descendant attribution, including descendants that leave their original process group. Keep signal handling, cancellation, and final reaping under a single coordinator. [Suite dispatch](/home/folk/Programs/pbfhogg/crates/verify/src/all.rs:36) [Check finalization](/home/folk/Programs/pbfhogg/crates/verify/src/harness.rs:501) [Process settlement](/home/folk/Programs/pbfhogg/crates/verify/src/process.rs:149) [Process-wide reap](/home/folk/Programs/pbfhogg/crates/verify/src/process.rs:368)

Start independent long producers early and overlap them with useful work on settled artifacts. For example, geocode's reference preparation has no dependency on either index build, and the two osmium OSC roundtrips can proceed once their respective change files exist. Use memory, CPU, and scratch-write admission limits. Two jobs that each saturate the same resource can extend the critical path, particularly for sorts, index builds, and external add-locations. Keep one result per check, grouped failure detail, and the existing distinction between comparison failure, environment failure, verifier error, and interrupt. Failure of an independent comparison still permits other checks to finish. [Geocode producer sequence](/home/folk/Programs/pbfhogg/crates/verify/src/checks/geocode.rs:1017) [OSC roundtrip dependencies](/home/folk/Programs/pbfhogg/crates/verify/src/checks/derive_changes.rs:107) [Result classification](/home/folk/Programs/pbfhogg/crates/verify/src/harness.rs:563)

## Local changes and findings

- **Medium-value local work.** Memoize validated tool identities and file digests inside the current cache, include hit work in step timing, and return order and counts from comparisons that already read them. These changes yield direct reductions with the existing process model. `stream::preview` also scans to EOF after it has the displayed lines and knows there are more. Stop after establishing that fact, and keep the complete listing on disk. This last change helps failure latency. [Preview implementation](/home/folk/Programs/pbfhogg/crates/verify/src/stream.rs:81)
- **Reference completion gap.** A fresh run with an accepted status and a missing declared output fails the cache's `completed` check, but execution still returns the accepted status and `Harness::reference` accepts it. The missing artifact is discovered downstream, where it can lose the producer-specific diagnostic. Make artifact presence part of the settled producer result. [Cache completion and placement](/home/folk/Programs/pbfhogg/crates/verify/src/reference_cache.rs:469) [Harness outcome check](/home/folk/Programs/pbfhogg/crates/verify/src/harness.rs:348)
- **Sorted-copy reuse is already partial.** Claimless-input consumers use the same simple-sort cache declaration. The gains there come from one run-local artifact and one identity check, with one production even on a fresh run. Treating the existing helper as an unconditional repeated sort would overstate the opportunity. [Sorted-copy helper](/home/folk/Programs/pbfhogg/crates/verify/src/verify_input_order.rs:57)

I would start with the change-family producers and the shared record source. They remove identifiable full-file work from warm runs as well as cold runs. Cache redesign then reduces the cost of retrieving the remaining oracle results, and scheduling can shorten the critical path with a smaller memory and scratch footprint.
