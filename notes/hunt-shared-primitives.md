I found three documentation defects. I did not establish a new data-corruption, concurrency, or partial-failure defect in the scoped implementation.

1. **`IdSet` promises an exact allocation boundary that it does not enforce.** [idset.rs:576](/home/folk/Programs/pbfhogg/crates/lib/src/idset.rs:576) says every ID above `pre_allocate(max_id)` will panic; the checked variants promise rejection instead. In fact, [dense_for_atomic](/home/folk/Programs/pbfhogg/crates/lib/src/idset.rs:728) checks only whether the ID's dense chunk exists. After `pre_allocate(1)`, `set_atomic_checked(2)` succeeds and `set_atomic(2)` does not panic. Automatic promotion through ordinary insertions also makes a chunk atomically writable without preallocation. The documentation is wrong: these methods check available dense storage, not the original numeric bound. I found no caller whose correctness currently depends on the stronger promise.

2. **The pipeline reference incorrectly says decoded kind claims cannot be checked.** [pipeline.md:116](/home/folk/Programs/pbfhogg/reference/pipeline.md:116) describes `repack` and `degrade` as unable to distinguish indexed blobs from replicated unindexed blobs at the worker boundary. The schedule now retains that distinction, and [ScheduledBlob::buffer](/home/folk/Programs/pbfhogg/crates/lib/src/scan/classify.rs:181) passes the claim into block validation, which refuses foreign kinds. The code is correct; this explanation is obsolete and contradicts `reference/indexdata-trust.md`.

3. **Spatial filtering's public documentation excludes the current index format.** [BlobFilter::with_node_bbox](/home/folk/Programs/pbfhogg/crates/lib/src/blob_meta/mod.rs:441) says it is effective only with v2 indexdata. [Deserialization](/home/folk/Programs/pbfhogg/crates/lib/src/blob_meta/mod.rs:337) also supplies spatial bounds from v3, which is what current writers emit. The documentation should say v2 and v3.

One additional coverage limit is worth flagging: **`check --refs` can pass a malformed leading header payload.** [consume_leading_header](/home/folk/Programs/pbfhogg/crates/lib/src/scan/classify.rs:530) checks the frame's type but never decodes its body; [check_refs](/home/folk/Programs/pbfhogg/crates/lib/src/commands/check/refs.rs:772) performs no separate header decode. A correctly framed `OSMHeader` with a one-byte payload `0x80` and no data blobs therefore reaches a successful empty reference report. I am not counting this as a confirmed defect because `--refs` explicitly promises referential integrity only, but its success does not certify that the header is readable.
